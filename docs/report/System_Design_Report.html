01
Executive summary

A focused system for reliable library operations.

The Library Management System is a responsive web application for operating a small library catalogue: it manages books, student and librarian profiles, borrowing, returns, sessions, and dashboard activity.

It was built as a single Spring Boot deployment with a static browser client. The project deliberately balances academic clarity with industry practices: REST contracts, service-layer transactions, DTOs, security boundaries, structured errors, test automation, and release documentation.

02
Context and intent

From a visual prototype to a durable operational system.

Problem statement

Browser-only state cannot operate a library.

A UI prototype can demonstrate navigation and form interactions, but it cannot securely manage identities, preserve loan history, enforce availability rules, or provide a trustworthy shared source of data.

Project objective

Build a responsive, maintainable library workflow.

Persist the catalogue and people records, process borrow/return transitions safely, protect operations by role, and document each important engineering decision.

Functional scope

  • Login, logout, profile, and session awareness
  • Dashboard activity totals
  • Books, students, and librarians management
  • Borrow and return workflows
  • Validation and structured error feedback

Quality targets

  • Responsive, accessible browser interface
  • Layered REST architecture
  • Safe password and session handling
  • Testable domain rules and persistence constraints
  • Clear technical and academic documentation

08
Protection in depth

Sessions are simple only when their boundaries are explicit.

SECURE
FLOWBCryptSessionRole checksCSRF

Authentication design

Spring Security uses DAO-based authentication against accounts, BCrypt password hashes, and an HTTP session. The browser client includes credentials on every request.

CSRF design

The application issues a readable XSRF-TOKEN cookie and forwards it in X-XSRF-TOKEN for unsafe requests. A SPA-aware request handler reconciles this with Spring Security’s masked-token handling.

Validation design

Jakarta validation runs server-side. The frontend retains the returned field errors and displays them beside matching inputs, avoiding generic feedback when useful detail is available.

!
Security hardening lesson. The login route may be public, but it is still a state-changing endpoint. CSRF protection therefore runs before authentication and must be tested with the actual browser cookie/header exchange.
09
Engineering diary

Issues became improvements when traced to their real boundary.

01

CSRF login rejection

Problem
Valid login attempts returned 403 before authentication.
Cause
The active Spring Security handler expected masked/XOR values while Fetch sent the raw cookie token.
Solution
A SPA-aware CSRF handler accepts the raw header token and preserves XOR handling for form flows.
Verification
Browser-equivalent MockMvc cookie/header test covers CSRF, login, session reuse, logout, and post-logout 401.
02

Duplicate ISBN response

Problem
A duplicate ISBN was reported as an unhelpful 500 error.
Cause
The database constraint exception was not transformed into an application conflict response.
Solution
Service checks and integrity-exception handling return 409 with a meaningful message.
Verification
Integration test asserts the exact conflict code and message.
03

Generic validation feedback

Problem
Invalid email feedback exposed only a generic validation summary.
Cause
Available API field errors were not mapped to modal fields.
Solution
Clear email messages and field-level error rendering were introduced.
Verification
Integration test asserts the email field’s Invalid email address. message.
04

Responsive density

Problem
Desktop navigation and dense data views need a narrow-screen counterpart.
Cause
Tables and horizontal navigation do not naturally fit mobile dimensions.
Solution
Responsive CSS introduces a compact navigation state, stacked dashboard grid, and scroll-safe tables.
Verification
Dedicated mobile captures document authentication, dashboard, validation, ISBN, and circulation states.

13
Reflection and next steps

Build the smallest complete system—then extend with evidence.

01

Security is a flow

Login success depends on session state, CSRF behavior, filter ordering, error handling, and browser request construction—not credentials alone.

02

Constraints need UX

Database integrity is necessary, but users need domain-oriented responses such as a clear ISBN conflict.

03

Tests should mirror users

Security test helpers are valuable, yet a dedicated raw cookie/header test prevented an SPA-specific regression.

04

Documentation compounds

Keeping contracts, decisions, tests, screenshots, and release notes together makes the final report credible and maintainable.

Catalogue scale

Pagination, richer search, categories, and physical-copy modelling.

Library services

Reservations, overdue processing, fines, notifications, and analytics.

Platform delivery

Swagger/OpenAPI, Docker, deployment automation, and operational monitoring.

Client evolution

JWT/API-client support only if the same-origin application model no longer fits the project.
